# 长会议纪要支持设计

## 目标

让会议录音在较长时长下仍能稳定生成纪要，避免把完整转写一次性放进模型上下文；录音、完整转写和最终纪要仍按现有目录保存，录音期间不阻塞桌面助手。

## 当前问题

录音结束后，当前流程直接把完整 WhisperX 转写传给配置的智能体。音频文件本身先保存在本地，因此主要风险不是音频大小，而是转写文字超过模型上下文或接口请求限制。

## 方案

采用分段摘要与最终合并的层级流程：

1. WhisperX 完整转写并保存原始 TXT/JSON。
2. 以 WhisperX 的时间戳/说话人行作为边界，优先在句末标点处分段；默认单段上限为 8,000 个字符。
3. 每段通过独立、无工具的智能体请求提取固定纪要结构：摘要、关键讨论、决策、待办和待确认问题。
4. 将各段结构化结果合并；当段数过多时先按批次合并，再继续归并，避免合并请求再次超过上下文。
5. 只把最终结构化结果写入现有 Markdown/JSON 纪要文件；原始转写路径继续写入 JSON 和 Markdown 引用。

## 组件边界

- `meeting_minutes.py`：负责转写分段、分段提示词、合并提示词、结构化结果归一化和持久化；不依赖 Tkinter、DeskOrb UI 或具体模型供应商。
- `worker.py`：在后台线程内顺序执行分段请求和归并请求，通过带前缀的事件通道向 UI 报告阶段进度；保留现有单次 `ask_meeting_minutes` 兼容接口。
- `deskorb_agent.py`：在转写完成后发起批处理请求，显示“第 N/M 段”和合并阶段，收到最终结构化结果后沿用现有保存逻辑。
- `config.py`：提供默认分段上限和合并批次上限，并允许环境变量覆盖。

## 长度与失败策略

- 默认分段上限：8,000 字符；实际切分只在完整行/句子边界处结束，超长单行再按标点或字符安全切开。
- 默认合并批次：最多 8 个分段摘要；批次结果继续进入下一层归并，因此长会议不会因为摘要数量线性增长而把一次请求撑爆。
- 任一分段请求失败时，批处理立即报告失败并保留录音、完整转写；不会写入一份看似完整但缺少内容的最终纪要。
- 合并请求失败时，保存已生成的分段摘要 JSON 作为诊断文件，并在 UI 中显示可重试提示。
- 用户停止录音后，转写和纪要生成仍在后台执行，正常聊天和 Office 功能不被锁定。

## 输出

最终文件路径保持不变：每场会议目录下的 `minutes/<stem>.md` 和 `minutes/<stem>.json`。JSON 增加 `chunk_count`、`summary_mode` 和可选的 `partial_summaries` 诊断信息；Markdown 继续展示合并后的摘要、关键讨论、决策、待办和待确认问题。

## 验证标准

- 纯函数测试证明长转写会在句子/行边界拆成多个片段，短转写保持原样。
- 合并提示词只包含分段摘要，不包含完整转写。
- 模拟 3 个分段的后台流程，确认请求顺序为“分段摘要 → 合并”，最终事件只产生一份结构化纪要。
- 模拟某个分段或合并失败，确认保存原始转写并报告错误，不产生错误的最终纪要。
- 现有会议录音、中文简繁转换和完整测试套件继续通过。
